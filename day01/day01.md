# 二、进程与线程

## 1. 什么是进程

进程可以理解为正在运行的程序实例。

一个进程拥有自己的运行资源，例如：

- 地址空间
- 内存
- 文件描述符
- 代码和数据
- 其他操作系统资源

进程是操作系统进行资源管理的重要单位。


## 2. 什么是线程

线程是程序中的一条执行路径。

一个进程内部可以包含多个线程。

例如：

- 主线程
- 工作线程 1
- 工作线程 2
- 工作线程 3

多个线程可以并发执行不同任务。


## 3. 同一进程中的线程有什么特点

同一个进程中的多个线程通常共享进程的大部分资源。

例如：

- 全局变量
- 堆内存
- 文件描述符
- 地址空间

但是每个线程拥有自己的执行状态，例如：

- 栈
- 寄存器
- 程序执行位置


## 4. 为什么使用多线程

多线程可以让多个任务并发执行。

常见用途：

- 后台任务
- 网络服务器
- 数据处理
- 视频流水线
- Producer-Consumer
- 图像处理
- 实时系统

十月份最终的视频流水线项目，本质上也会使用多个线程分别完成 Capture、Detect 和 Track。


# 三、主线程与工作线程

## 1. 什么是主线程

程序从 main 开始执行时，就已经存在一个线程。

这个线程通常称为：

主线程。


## 2. 什么是工作线程

程序运行过程中额外创建出来的线程，可以称为：

工作线程。


## 3. 一个进程可以有多少线程

一个进程可以同时存在多个线程。

例如：

进程

- main thread
- worker thread 1
- worker thread 2
- worker thread 3


# 四、std::thread

## 1. std::thread 的作用

std::thread 是 C++ 标准库提供的线程类。

它用于：

创建和管理线程。


## 2. 创建线程意味着什么

创建一个线程以后，会产生一条新的执行路径。

主线程和工作线程可以继续各自执行任务。


## 3. 一个重要认识

创建线程之后：

工作线程什么时候真正运行，并不完全由代码书写顺序决定。

操作系统会负责线程调度。


# 五、线程调度

## 1. 什么是线程调度

当多个线程都可以运行时，操作系统会决定：

哪个线程先获得 CPU。

这就是线程调度。


## 2. 线程执行顺序是否固定

不固定。

例如创建线程的顺序可能是：

1
2
3

实际开始执行的顺序却可能是：

1
3
2

也可能是：

2
1
3


## 3. 为什么每次运行结果可能不同

因为线程运行受到操作系统调度影响。

不同线程获得 CPU 的时机可能不同。

因此：

多线程程序的执行顺序通常具有不确定性。


# 六、创建顺序、执行顺序、完成顺序

这是今天最重要的区别之一。

## 1. 创建顺序

表示程序按照什么顺序创建线程。

例如：

先创建线程 1

再创建线程 2

再创建线程 3


## 2. 执行顺序

表示线程实际上获得 CPU 并开始执行的顺序。

执行顺序通常不能单纯通过创建顺序判断。


## 3. 完成顺序

表示哪个线程最先完成任务。

完成顺序还会受到：

- 任务耗时
- CPU 调度
- 系统负载

等因素影响。


## 4. 结论

创建顺序不等于执行顺序。

执行顺序不等于完成顺序。


# 七、join

## 1. join 的核心含义

join 表示：

当前线程等待目标线程执行结束。


## 2. main 中调用 join 的含义

通常表示：

主线程等待工作线程结束，然后再继续执行。


## 3. join 是否负责启动线程

不是。

线程在创建时就已经具备运行条件。

join 的作用只是：

等待线程结束。


## 4. join 最容易产生的误解

错误理解：

先调用哪个 join，哪个线程就先执行。

正确理解：

join 决定的是主线程等待哪个线程。

它不决定工作线程的运行顺序。


## 5. join 顺序和线程完成顺序

即使主线程按照：

线程 1

线程 2

线程 3

的顺序等待，

线程 2 仍然可能在线程 1 之前完成。


## 6. 为什么线程通常需要 join

如果一个线程对象仍然管理着一个可 join 的线程，而线程对象直接被销毁，程序可能触发异常终止。

因此线程生命周期必须被正确处理。


# 八、joinable

## 1. joinable 是什么

joinable 用于判断：

当前 thread 对象是否关联着一个可以进行 join 的线程。


## 2. 刚创建线程后

通常：

joinable 为 true。


## 3. join 之后

joinable 为 false。


## 4. detach 之后

joinable 也为 false。


## 5. joinable 不代表什么

joinable 不等于：

线程此刻一定正在 CPU 上运行。

它描述的是：

thread 对象当前是否关联着一个可 join 的线程。


## 6. 一个重要细节

即使线程中的任务已经执行结束，如果还没有进行 join 等生命周期处理，thread 对象仍然可能处于 joinable 状态。


# 九、detach

## 1. detach 的含义

detach 表示：

让工作线程与当前 std::thread 对象解除关联。


## 2. detach 后会发生什么

detach 后：

thread 对象不再负责等待这个工作线程。

工作线程可以继续独立运行。


## 3. detach 后 joinable 状态

detach 后：

joinable 为 false。


## 4. detach 与 join 的核心区别

join：

等待线程结束。

detach：

不再等待线程，让线程独立继续运行。


## 5. detach 不代表线程一定执行完成

即使线程已经 detach，它仍然属于当前进程。

如果整个进程结束：

该线程也无法继续存在。


## 6. 为什么 detach 要谨慎

因为 detach 后：

主线程很难再直接控制该线程的生命周期。

还需要特别注意：

- 访问已经失效的数据
- 主线程结束
- 对象被销毁
- 资源生命周期

因此实际工程中应谨慎使用 detach。


# 十、join 与 detach 对比

## join

含义：

等待目标线程结束。

特点：

- 可以保证目标线程完成后再继续
- 生命周期更容易管理
- 工程中非常常见


## detach

含义：

让线程脱离 thread 对象独立运行。

特点：

- 当前 thread 对象不再管理它
- 无法再通过这个 thread 对象 join
- 生命周期管理更加困难
- 使用时需要更加谨慎


# 十一、线程 ID

## 1. 什么是线程 ID

每个线程都有自己的线程标识。

线程 ID 可以用于区分不同线程。


## 2. 主线程和工作线程 ID

主线程有自己的线程 ID。

每个工作线程也拥有自己的线程 ID。

不同线程通常拥有不同 ID。


## 3. 当前线程 ID

获取当前线程 ID的含义是：

获取目前正在执行当前代码的线程 ID。


## 4. thread 对象的线程 ID

thread 对象也可以获取它当前关联的工作线程 ID。


## 5. 今日实验得到的关系

主线程 ID：

与工作线程 ID 不同。

某个 thread 对象管理的工作线程 ID：

与该 worker 内部看到的当前线程 ID 相同。


# 十二、多线程输出交错

今天运行多个线程时观察到了输出内容混在一起的情况。

例如：

多个线程同时向终端打印内容。

最终可能出现：

两条本来独立的信息被拼接到一起。


## 原因

多个线程可能同时执行输出操作。

线程之间的运行时机不固定。

因此输出可能发生交错。


## 当前阶段需要记住

不要假设多个线程的输出一定按照完整的一行一行执行。

后续学习 mutex 时会进一步解决类似的并发同步问题。


# 十三、线程对象生命周期

这是今天非常重要的知识点。

## 1. 创建线程后不能完全不管

一个线程创建以后，需要考虑：

它什么时候结束。

谁负责等待。

thread 对象什么时候销毁。


## 2. joinable thread 对象直接析构

如果 thread 对象仍然处于 joinable 状态，却直接析构：

程序可能调用 std::terminate，导致程序异常终止。


## 3. 因此线程退出前需要正确处理生命周期

典型方式：

- join
- detach


# 十四、今天实际观察到的异常

将 join 去掉以后：

主线程快速结束。

thread 对象仍然关联着线程。

thread 对象析构时发现仍然 joinable。

最终程序出现：

terminate

并被系统中止。


## 这个实验说明什么

创建线程后：

必须认真管理线程生命周期。

不能认为：

主线程结束以后工作线程自然就没有问题。

# 十六、LeetCode 226 翻转二叉树

## 1. 题目本质

翻转二叉树的本质是：

对树中的每一个节点，都交换它的左孩子和右孩子。


## 2. 为什么适合递归

一棵二叉树由：

根节点

左子树

右子树

组成。

翻转整棵树以后：

左右子树也需要执行完全相同的操作。

因此适合使用递归。


# 十七、递归必须理解的三个部分

## 1. 递归函数的任务

当前函数负责：

翻转以当前节点为根的整棵树。


## 2. 递归终止条件

当当前节点为空时：

已经没有节点需要处理。

此时结束递归。


## 3. 递归过程

每到达一个有效节点：

先处理当前节点。

然后让左右子树继续完成相同任务。


# 十八、翻转二叉树的核心思路

翻转一棵二叉树可以分成：

第一步：

判断当前节点是否为空。

第二步：

交换当前节点的左孩子和右孩子。

第三步：

递归翻转左子树。

第四步：

递归翻转右子树。

第五步：

返回当前根节点。


# 十九、为什么交换的是孩子而不是数值

翻转二叉树要求改变的是：

树的左右结构。

因此核心是交换：

左孩子与右孩子之间的关系。

不是简单交换两个节点中的数值。


# 二十、递归的理解方式

今天最重要的递归理解：

不要试图一次想完整棵树。

只考虑当前节点需要完成什么。

当前节点负责：

交换自己的左右孩子。

然后：

把完全相同的问题交给自己的左右子树。


# 二十一、递归展开过程

假设根节点有左右两个子树。

首先：

处理根节点。

然后：

进入左子树。

左子树继续做同样的操作。

当遇到空节点时：

递归返回。

左子树结束后：

继续处理右子树。

最后：

整棵树全部处理完成。


# 二十二、递归为什么能够返回上一层

每次调用函数时：

系统都会保存当前函数的执行状态。

当下一层递归执行完成以后：

程序会回到上一层递归调用的位置继续执行。

这依赖函数调用栈。


# 二十三、今天 LeetCode 必须能说清的问题

## 问题 1：为什么翻转二叉树可以用递归

因为左右子树与整棵树具有相同的问题结构。

每个节点都执行相同操作。


## 问题 2：递归终止条件是什么

当前节点为空。


## 问题 3：当前节点要做什么

交换左右孩子。


## 问题 4：当前节点交换完成后为什么还没有结束

因为左右子树内部也需要继续翻转。


## 问题 5：递归最重要的思维是什么

只考虑当前一层负责什么。

把剩余的相同问题交给下一层递归。


# 二十四、今日易错点

## 易错点 1

认为创建线程的顺序就是执行线程的顺序。

错误。

线程执行受到操作系统调度影响。


## 易错点 2

认为 join 是启动线程。

错误。

线程创建后已经可以运行。

join 只是等待。


## 易错点 3

认为先 join 的线程一定先执行完成。

错误。

join 顺序只是主线程的等待顺序。


## 易错点 4

认为 detach 后线程一定可以完整运行。

错误。

进程结束以后，detached 线程也无法继续存在。


## 易错点 5

认为 joinable 表示线程正在 CPU 上运行。

错误。

joinable 表示 thread 对象当前是否关联一个可 join 的线程。


## 易错点 6

创建线程后直接让 thread 对象析构。

如果仍然 joinable，可能导致程序异常终止。


## 易错点 7

认为多线程输出一定严格一行一行执行。

错误。

不同线程的输出可能交错。


## 易错点 8

写递归时忘记终止条件。

这样可能导致无限递归或者非法访问。


## 易错点 9

做翻转二叉树时只交换根节点。

错误。

整棵树中的所有节点都需要执行相同操作。


## 易错点 10

递归时总想一次理解整棵树。

更好的方法是：

只明确当前层做什么。

剩余问题交给递归处理。
